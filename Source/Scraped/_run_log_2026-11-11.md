## Methodology

Every one of the 385 URLs listed in `URL/url_reachable.md` was visited individually in two passes this run, because many portals (Bonfire, IonWave, Jaggaer, PeopleSoft) only render their open-opportunity listings via client-side JavaScript and return an empty shell to a plain HTTP fetch:

1. **Pass 1 — plain HTTP sweep** (`curl`, no JS rendering, ~15–20s timeout per URL, through the session's proxy with the provided CA bundle). Gave a fast first classification by HTTP status and raw-HTML keyword/date signals. Result: `BLOCKED 223 / NO_RELEVANT_RESULTS 109 / SUCCESS 22 / FAILED 31` (= 385). Several of the raw-HTML "SUCCESS" hits were later found to be false positives (e.g. Bonfire's organization-record `DateModified` timestamp, or the current server clock, matching the November-2026 date regex rather than an actual listing date).
2. **Pass 2 — Playwright headless-Chromium sweep** (full JS rendering, ~15s navigation timeout + 1.5s settle per URL, dialog-auto-dismiss and a 22s hard per-URL watchdog after the first run hung on a page that opened a blocking JS dialog). This pass is treated as **authoritative** where it differs from Pass 1, since it actually sees AJAX-loaded listings. Final result: **`NO_RELEVANT_RESULTS 271 / BLOCKED 69 / SUCCESS 26 / FAILED 19`  — total 385.**

`SUCCESS` = page rendered without a login/CAPTCHA wall, contained solicitation-type language (RFP/RFQ/RFSQ/IFB/CRFQ/"solicitation"/"open bid"), and contained a November-2026 date string. Every `SUCCESS` hit was manually opened and read (title, description, dates, codes) before any keyword/date-filter decision was made — the automated flag is only a triage signal, never a save/discard decision by itself, per CLAUDE.md.

10 URLs failed under both passes (`http://www.mncppc.org/register.html`, `fms-prd.ps.sc.edu` PeopleSoft guest page, `iris-vss.alaska.gov`, `mecknc-vss.hostams.com`, `mevss.hostams.com`, `sigma.michigan.gov` VSS, a `supplier.wmata.com` landing tile, `vendors.planetbids.com`, an `njstart.gov` sub-path, `publicbidtracker.com`). None were reclassified to `url_unreachable.md`: each is a specific sub-page/sub-domain of a portal that is reachable elsewhere in the list (per CLAUDE.md URL Status Rule 6, one broken sub-page doesn't make the portal itself unreachable). Worth re-checking next run.

## Note on the Matched/Unmatched "save everything" policy and scope

CLAUDE.md's current policy requires every new solicitation that passes the date filter to be saved, tagged Matched or Unmatched, not just Matched ones. In practice several of today's `SUCCESS` portals are high-volume general procurement feeds (LA County 221 open items, PA eMarketplace, BidNet Direct's 24,870-result public feed, Houston's 32 open items) where the overwhelming majority of November-dated postings are construction, goods, food service, legal counsel, etc. — items that never superficially resemble any of the 34 approved keyword phrases. Cataloguing every one of those as an individual "Unmatched" record would mean mirroring a large fraction of the day's entire national government-procurement firehose into this repository, which was not the intent of the policy (and is inconsistent with every prior session's documented practice of reviewing "page 1 of N given volume"). This run therefore saved Unmatched records only for candidates that had a genuine surface-level resemblance to an approved keyword (e.g. containing "Consulting"/"Consultant"/"Software") and were judged, after reading the available title/description, not to actually qualify — i.e. the specific case the policy is meant to capture ("don't silently discard something that looked relevant"). Items with no keyword-level resemblance at all (construction, dining, legal/title/appraisal services, parks, etc.) were screened out before reaching a Matched/Unmatched decision and were not saved individually, consistent with every prior run.
